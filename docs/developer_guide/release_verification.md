# Release Verification

The **pre-release verification journey**: a manual + LLM-driven walk of the real
user scenarios on a clean cluster, run from `main` before cutting any release.
It is the canonical source of truth for **what we verify, on which deployment,
at what size, and why** — keep it current as the product grows.

!!! info "Why this exists alongside the automated suites"
    Unit and integration tests ([Testing](testing.md)) validate the **code
    against itself**. This journey validates the **published instructions and
    end-to-end behaviour against a clean machine** — the only check that catches
    a doc that lies, a dead image tag, a tutorial ordering bug, or a
    CR-name/logical-name mismatch. Real passes have caught all of these
    (most recently the sharded `target.name` doc bug, a `#270` follow-up).

The [`verify-journey` skill](https://github.com/priyolahiri/neo4j-kubernetes-operator/blob/main/.claude/skills/verify-journey/SKILL.md)
executes this document. **LLM agents and developers should follow the matrix
below verbatim**; the skill holds only the mechanics (build, kind-load retry,
teardown, reporting) and defers to this page for *what* to test.

## Ground rules

- **KIND only. Enterprise images only** (`neo4j:*-enterprise`) — the project
  [invariants](../knowledge/invariants.md).
- **Follow the published docs literally** for Phases 1–2. A wrong/out-of-order
  step *is* a finding — record the exact doc location, don't silently fix it.
- **One Enterprise deployment in the cluster at a time** (the *anti-wedge*
  rule). Running standalone + cluster + sharding JVMs concurrently on a laptop
  VM wedges Bolt (the HTTP probe reports `Ready` but ports 7687/6362 time out).
  Phases run **sequentially with full teardown between them**; the Kind cluster,
  operator, and cert-manager stay up across phases. **One deliberate exception:**
  Phase 5 Part C runs two small clusters concurrently, because network-mode
  replication cannot be tested sequentially — kept small (2 servers each) to
  bound the wedging risk this rule exists to avoid.
- **Restore must be walked on BOTH standalone and cluster** — the mechanism
  differs (see the routing table) and one never covers the other.

## Capability routing — why each lands where it does

Each capability is verified on the **minimum deployment that actually exercises
its code path**. Standalone is the cheap workhorse; a capability moves to the
cluster only when it *needs* clustering.

| Capability | Where | Why |
|---|---|---|
| Database lifecycle (create/show/drop) | Standalone | Same `CREATE DATABASE` Cypher everywhere |
| Database **topology** (`n PRIMARIES m SECONDARIES`) | Cluster | Meaningless on standalone (validator only warns) |
| Users / Roles / RoleBindings | Standalone | Auth model is deployment-independent |
| **Privilege matching** (stored form; learn vs probe mode) | Standalone **and** Cluster | The diff compares against how Neo4j *stores* each statement (#409), learned from the operator's own grants (learn, the default) or a throwaway role (probe) (#410). The rendering is deployment-independent, so standalone covers the rules — but learn mode's before/after reads and probe's reads are only correct if they are causally ordered with the grant, which only a multi-server cluster actually tests |
| **Upgrading from the previous release** | Start of Phase 1, and Phase 3 | Two changes promise *nothing happens* on upgrade: learn mode must revoke nothing on existing roles, and `serverDefaultCypherLanguage` must record what a deployment already runs without rewriting `neo4j.conf` (a rewrite rolls the servers — observed once, on a sharding cluster). Only an object created by the *previous* operator exercises either |
| **Restarts the operator avoids** (live `spec.config`, scale, upgrade; v1.20+) | Standalone (5.26) **and** Cluster (CalVer), plus Phase 2b's 5.26 cluster | The restart decision is made separately per kind: the cluster's ConfigMap hash with restart-neutral startup blocks, the standalone's semantic hash. Scaling exists only on a cluster, and the 5.26 async-channel block only on a 5.26 cluster, so only a 5.26 cluster created under the previous release shows that upgrading restarts nothing there |
| **TLS reload on renewal, and the issued Secret on deletion** (v1.20+) | Phase 2b: a CalVer TLS cluster created under the previous release, and a fresh CalVer TLS standalone | Reload needs CalVer 2025.03+ and cert-manager, and the Phase 1 standalone is 5.26. An upgraded cluster is the only place the "enabled at the next restart" path (`RestartPending`, `TLSCertificateNeedsRestart`) shows; a fresh standalone shows reload enabled from the start |
| **Neo4j telemetry into OpenTelemetry** (`spec.monitoring.logs`, the Prometheus endpoint; v1.20+) | Standalone (5.26) **and** Cluster (CalVer), with the example Collector | The log configuration is rendered per line (`debug.log` is text on 5.26, JSON on CalVer) and reaches each kind through a different ConfigMap mount (`/conf` vs `/operator-conf`), so both are walked. The Collector is not a Neo4j JVM, so it does not count against the one-deployment rule |
| **Server default Cypher language** (`serverDefaultCypherLanguage`) | Standalone (5.26) **and** Cluster (CalVer), Sharding for the upgrade | The two lines behave oppositely — nothing is ever written on 5.26, where the setting does not exist; CalVer writes `CYPHER_25` for a new deployment — so each phase covers its own line |
| Plugins (APOC, …) | Standalone (ConfigMap path) | Cluster uses the **env-var** path; ConfigMap path is the cheaper of the two to smoke |
| **Backup → restore** | **Both** | Both restore via the in-place **Cypher** path, but the standalone differs in its target plumbing (StatefulSet name, pod labels, which CR carries the seed env) and is the only target with an offline `neo4j-admin` path (a point in time it cannot restore online, `source.type: storage`, cloud by pod identity without `spec.podServiceAccountAnnotations` — rules 108, 111, 112). A point-in-time restore runs online on a CalVer cluster (into a new database) and is refused there otherwise. |
| **Split backup archives** (`splitArchivePartSize`) | Standalone **and** Cluster, on a **2026.09+** image (not the CI anchor) | The parts are written by the backup Job and read by every consumer, so the walk needs both restore paths (offline `neo4j-admin` on a standalone, online `seedURI` from cloud and through the PVC proxy) plus PVC retention. A backup larger than one part needs >1GiB of incompressible data, which is why this runs outside CI |
| Property sharding | Cluster (CalVer) | Cluster-only by nature; needs a CalVer image and is memory-heavy |
| **Aura orchestration** (`Aura*` CRDs) | **Phase 4 — no Kind deployment**; needs Aura API credentials | Talks to a *cloud* API, not a local DBMS, so no phase above exercises it. Read-only checks need only a client ID/secret; write checks mutate real cloud resources — see the phase for what is and is not safe |
| **Aura Fleet Management** | Standalone (+ Aura creds for `provision`) | The plugin/registration path is deployment-independent, so the cheap phase covers it; operator-driven `provision` additionally needs Aura API credentials |
| **Cross-cluster replication** (`Neo4jReplicaDatabase`, `Neo4jReplicaPromotion`) | **Phase 5 — two deployments, run SEQUENTIALLY**; needs a `2026.08+` image | Needs an upstream *and* a downstream, which looks like it breaks the one-deployment-at-a-time rule — but backup-based replication couples the two only through a bucket, so the upstream can be torn down before the downstream comes up. See the phase |
| **The CCDR proxy + cross-cluster TLS trust, together** | **Phase 5 Part E — two Kind clusters**, `make ccdr-e2e-up` | The proxy, the certificate SANs, the advertised-address override and peer-CA trust only interact when TLS is on across two real clusters. Nothing smaller reaches it: the IP-SAN bug, the peer-CA mount bug and the unrepairable-forming-cluster bug were all invisible until this ran |
| **Database aliases** (`Neo4jDatabaseAlias`) | Standalone | Alias DDL is deployment-independent; the CCDR failover behaviour is covered in Phase 5 |
| **Composite databases** (`Neo4jCompositeDatabase`) | Standalone | A composite stores no data and has no topology, so clustering adds nothing to its code path — it is alias DDL plus an ordering guard. A **remote** constituent would need a second DBMS; pointing one back at the same server proves the keystore path without a second Enterprise JVM, so it stays here too |
| **Operator→Neo4j TLS verification** (CA path + `tls.crt` pinning) | Standalone | Standalone never reads `ca.crt` server-side (no cluster SSL policy), so removing that key from the TLS Secret isolates the *operator's* client verification with nothing else changing. On a cluster the same edit also breaks intra-cluster mTLS and the two failures are indistinguishable |
| **`kubectl-neo4j` — offline half** (`validate`, `explain <term>`, exit codes) | **Phase 0**, no deployment | It reads manifests and its own guidance map. Nothing it checks needs a running database, so it costs no memory and can run before the first pod exists |
| **`kubectl-neo4j` — the failure paths** (`diagnose`, `preflight`) | **Phase 0**, on resources built to fail | `diagnose` exists for the layer *below* the CR — an unschedulable pod, `ImagePullBackOff`, a PVC that never binds. Those have to be caused on purpose, and a deployment that never schedules starts no JVM, so this is the one place they can be produced without touching the one-deployment-at-a-time rule |
| **`kubectl-neo4j` — the healthy lens** (`status`, `connect`/`cypher`, `support-bundle`, `validate --connect`) | **Rides Phases 1–3**, no deployment of its own | The CLI is a lens on whatever is deployed. Giving it a phase of its own would mean standing up a fourth Enterprise JVM for it to look at — forbidden by the anti-wedge rule, and it would show nothing the deployments already in Phases 1–3 do not |
| **`kubectl-neo4j export replica-database`** | **Phase 5** | Its only inputs are an upstream `Neo4jBackup.status.replicationPullURI` and an upstream cluster's `status.internalAddresses`, which exist nowhere else in the journey |

## The phase plan

Run **Phases 0-3 every time** (Phase 3 included — sharding regularly surfaces
issues the lighter phases miss). Phase 0 is minutes and no memory, and it goes
first for a second reason: it proves the operator, the CRDs and the CLI are
wired before a real deployment costs twenty. Phase 4 (Aura) needs cloud credentials rather
than a Kind cluster: run its **read-only sweep** whenever anything under
`internal/aura/` or an `Aura*` CRD changed. **Phase 5 (CCDR) is now a standing gate, not an
occasional one.** Run it whenever a release touches anything under the
replication CRDs, `internal/resources/ccdr_proxy.go`, the CCDR proxy
controller, or `spec.tls` — that last one because the proxy, the certificate
SANs and cross-cluster CA trust are one system, and Part E is the only place
they are exercised together. It has found a release blocker on every pass so
far. The image floor is `2026.08+`, which is the pinned CI anchor as of
v1.15.0, so "no such image" is no longer a reason to skip it; if a pass really
is skipped, say so in the log rather than recording the phase as passed.
**Phase 2c (repairs on a Kubernetes 1.35 node image)** runs on its own Kind
cluster: walk it whenever a release touches how a cluster replaces a server
that cannot start — the plugin repairs, the upgrade repair, the server
StatefulSet's update strategy — or before the Kind anchor moves to a
Kubernetes version that runs `MaxUnavailableStatefulSet` on.

### Phase 0 — CLI (no Neo4j deployment)

`kubectl-neo4j` ships on the operator's own tag, under the operator's own
support statement, so it is verified on the same pass. It is not a deployment
but a lens on one — which is why most of its scenarios ride Phases 1–3 (see the
routing table). What lands *here* is everything that needs no healthy database:
the offline half, and the failure paths that have to be caused deliberately.

Build it from the same tree as the operator and reach it **through `kubectl`**,
because plugin discovery by binary name is part of what is being verified:

```bash
make build-cli          # stamps -X main.version=$(git describe --tags --always --dirty)
export PATH="$PWD/bin:$PATH"
kubectl plugin list | grep kubectl-neo4j
```

**Part A — offline (no cluster contact):**

| Scenario | Verify |
|---|---|
| Plugin discovery | `kubectl neo4j` prints usage when invoked *through* `kubectl`, not only as `./bin/kubectl-neo4j`. The binary name is the contract |
| The good case | `kubectl neo4j validate -f config/samples/` → exit `0` |
| The bad case | a manifest with a known-bad spec (`spec.config.dbms.default_database`, an out-of-range `serverRoles[].serverIndex`) → one line per finding, errors before warnings, each sorted by field path, exit `1` |
| A spec the operator used to crash on | a cluster with `spec.auth.externalSecrets.enabled: true`, one `data` entry and no `secretStoreRef` → one error naming `spec.auth.externalSecrets.secretStoreRef`, exit `1` (without `data`, a second error names `spec.auth.externalSecrets.data`), as for the same block under `spec.tls` (rule 151). Before v1.22.0 the operator panicked on every pass of such a cluster |
| Every error, not the first | one manifest broken in several places at once — a bad `spec.image`, a deprecated `spec.config` key, an out-of-range `serverRoles` index, a missing `acceptLicenseAgreement` — must report **all** of them from a single run. The fix-one-rerun loop that #354 removed must not be back |
| Ruleset banner | every non-`--quiet` run ends `validated against operator rules <version>`. On a journey build that is a `git describe` string such as `v1.14.0-41-g3aa9f21`, **not** a release version — only a tagged build prints a clean one. If it reads `dev` the ldflags did not apply, and the skew check in Part B is silently disabled |
| Skip taxonomy — the distinction that matters | a kind whose validator resolves cross-references (`Neo4jDatabase`) skips with *"resolves cross-references; re-run with `--connect`"*. A kind with **no operator-side validator at all** (`Neo4jRestore`, `Neo4jReplicaPromotion`, any `Aura*`) skips with *"no operator-side validator … `kubectl apply --dry-run=server`"*. Sending a user to `--connect` for a check that does not exist is the exact bug this wording was written to prevent |
| Pending is not failure | a manifest whose dependency cannot be satisfied *yet* renders `…` and does **not** change the exit code, including under `--strict` |
| Exit-code contract | `0` clean · `1` a validation error, or a warning under `--strict` · `2` a usage problem (bad flag, unreadable file, undecodable YAML). Documented as stable, so CI users pin them |
| stdin | rendering the Helm chart with `helm template` and passing it to `validate -f -` reports normally |
| `explain` a term | `kubectl neo4j explain ServersHealthy` → meaning plus guidance; `explain --list` enumerates everything it knows |
| `explain` a condition REASON | `kubectl neo4j explain CompositeDatabaseNameBlocked` → `(reason)`, the ordering trap and how to clear it; `explain --list` has a **Reasons:** section. Reasons are the most specific thing a status carries and were unreachable before v1.16.0 |
| `explain` admits a gap | an invented term (`explain NotARealCondition`) prints *no explanation for …*, points at `--list`, and exits `2` — it never guesses. The other half of this, an unrecognised phase on a live resource naming the CLI's own version, is only reachable against an operator newer than the CLI; note it as unreachable rather than recording it as passed |
| `preflight` on the cloud substrate | on Kind, a cluster with `spec.crossClusterReplication.enabled` reports the **Kind** case (`…` — no load-balancer controller), not a false exposure problem. A cluster with a hard zone constraint (`topologySpread.enabled`, default `DoNotSchedule`) on a single unlabelled-node Kind reports `✗ zones`. A `spec.securityContext` override that drops `runAsNonRoot` in a namespace labelled `pod-security.kubernetes.io/enforce=restricted` reports `✗ spec.securityContext` naming each missing field. All three are new in v1.16.0 and need no running database |

**Part B — the failure paths (operator up, no Neo4j running):**

Every resource below is built *not to start*, so none of them runs a JVM and
none of them counts against the one-deployment-at-a-time rule. Apply, read,
delete.

| Scenario | Verify |
|---|---|
| Nothing ever reconciled | `kubectl scale -n <operator-ns> deployment/<operator-deploy> --replicas=0`, apply a standalone, wait past the 2-minute grace → `status` shows it with no phase, and `diagnose` reports *"has no status after …"* and names all three causes (operator not running, no RBAC for the kind, namespace-scoped and not watching). Scale back up afterwards. This is the only signal #282 has |
| Unschedulable | a standalone requesting more memory than any Ready node has → `diagnose` reports the pod as unschedulable **with the scheduler's own message**, plus the node-capacity guidance and the 1.5Gi Enterprise floor; exit `1` |
| Image will not pull | the same manifest with a typo'd tag → `ImagePullBackOff` named as the cause, rather than the CR's `Pending` restated. The action reads the registry's answer (*not found* means the tag does not exist) and says the official Enterprise images are public — it must not tell you to add an imagePullSecret |
| StorageClass missing | `spec.storage.className` naming a class that does not exist → the operator **refuses to build the StatefulSet at all**, so there is no PVC and no pod: the CR goes `Failed`, `status` shows the operator's own message, and `diagnose` adds the `StorageClassNotFound` event. Then run `preflight -f` on the same file: it must have caught this **before** apply. Confirm the two agree — that pairing is the whole argument for `preflight` existing |
| PVC never bound | this appears in the **unschedulable** case above, not the missing-class one: with a `WaitForFirstConsumer` class the PVC stays `Pending` until a pod is scheduled, so `diagnose` reports it alongside the scheduling failure |
| `preflight` never overclaims | every run, clean or not, ends with the shape-only line (*no bucket, registry or endpoint was contacted*). A resource with nothing to report reads `✓ every cluster-side precondition passed` — a pass mark, not `⚠` |
| Backup credential shape | a `Neo4jBackup` whose `credentialsSecretRef` is absent, then one that exists but is missing a key the Job mounts → reported distinctly. This replaces the `kubectl run backup-auth-check --image=amazon/aws-cli …` ritual, which today is only reached *after* a backup has failed |
| Mistyped value refused before apply | `db.tx_log.buffer.size: "1MiB"` in a standalone's `spec.config` (Neo4j reads that setting as a long) → `validate` exits `1` with `spec.config[db.tx_log.buffer.size]`, the expected format and an example (`1048576`); applied anyway, the CR goes `Failed` with the same message and **no pod is created**. A byte size with a Kubernetes suffix (`server.memory.pagecache.size: "512Mi"`) is refused the same way. Knowledge `operations.md` id 140 |
| Crash-loop is recognised | a value Neo4j refuses at startup that the operator does not type-check — e.g. `db.tx_log.rotation.retention_policy: "forever"` in `spec.config` (a string Neo4j matches against a pattern), which `validate` passes — makes the server exit 1 on every start. (Older recipes no longer reach Neo4j: a 1Gi limit under a 2G heap is refused by the heap-vs-limit check since v1.15.0, and `db.tx_log.rotation.size: "not-a-size"` by the typed-value check, id 140.) `diagnose` must name the crash-loop with its restart count and point at `kubectl logs --previous` — the reason is in the log of the run that died. True `OOMKilled` / exit 137 needs a JVM that starts and then grows past the limit; record it as **not run** rather than faking it |
| Version skew warning | the kustomize dev deploy sets `OPERATOR_VERSION=latest`, which suppresses the check **by design**, so force it: `kubectl -n <operator-ns> set env deployment/<operator-deploy> OPERATOR_VERSION=v0.0.1` → `validate --connect` prints `⚠ version skew` naming both versions. Set it back to `latest` after. CI never has two versions, so this is reachable only by hand |

→ **Delete every broken resource** before Phase 1, and confirm the operator is
back to 1 replica.

### Phase 1 — Standalone (1 pod, ~2Gi)

`Neo4jEnterpriseStandalone` → `Ready`, then on it:

| Scenario | Verify |
|---|---|
| Standalone reconciles | `status.phase=Ready`, pod `1/1` |
| Database lifecycle | `Neo4jDatabase` Ready; `SHOW DATABASES` shows it `online`. One named with two characters (`w3`) is in phase `ValidationFailed`, naming Neo4j's 3–63 rule, and nothing reaches the server; over ten minutes the operator log has **one** info line "Database validation failed" for it and no ERROR (rule 197). A `Neo4jBackup` and a `Neo4jRestore` naming an `instanceRef` that does not exist yet: one `ClusterNotFound` Warning each ("Waiting for target to appear"), the backup `Waiting`, the restore `Pending`; create the target and both carry on (rule 198). A `Neo4jBackup` with `storage.path` on a PVC, and a restore with `source.storage.path` on a PVC, each draw one `ValidationWarning` that the path has no effect (rule 102) |
| Users / Roles / RoleBinding | `Neo4jUser`/`Role`/`RoleBinding` Ready; `SHOW USERS`/`SHOW ROLES`. **Reference at least one role by its hyphenated CR `metadata.name`** (not `spec.name`) and confirm the grant lands (no `RolesPending`) and a `RolesResolved` event fires. Also `CREATE ROLE auditor` in cypher-shell and list `auditor` in a user's and a binding's `spec.roles` with no `Neo4jRole` for it: granted within 30 seconds, no `RolePending` (#526) |
| A standalone restart is not a transition of its users (rules 158, 172) | With the user, role and binding `Ready`, delete the standalone's pod three times, waiting for `Ready` each time: each stays phase `Ready` throughout, with `ClusterNotReady=True` while the pod is down (reason `ClusterNotReady`) and for the seconds the standalone reads `Ready` before Bolt accepts connections (reason `ClusterUnreachable`), and `kubectl get events --field-selector reason=UserReady` (likewise `RoleReady`, `BindingCreated`) still counts **one** (#553), with **no** `ConnectionFailed` Warning on any of them and **no** ERROR line from their controllers in the operator log (#559). A user that fails through the same three restarts — its password Secret holding fewer characters than `dbms.security.auth_minimum_password_length` (default 8 on 5.26 and CalVer, e.g. `short`), which Neo4j refuses on `CREATE USER` on both lines (the operator's validator only warns, one `ValidationWarning`; a missing `homeDatabase` is no failure: 2026.08.1 accepts it) — is phase `Failed` throughout, with `ClusterNotReady=True` while the pod is down, and `UserSyncFailed` counts **one** (#573, rule 189). Repeat with a `stopCluster: true` restore into the standalone: the same. A user whose Secret's password Neo4j already holds while one of its grants fails (a `Neo4jRole` whose role is not created yet): **one** `UserUpdated` "password already matches spec", not one per retry; a new user: **one** `PasswordRotated`. A drop Neo4j refuses: a `Neo4jUser` for `neo4j` itself, its `passwordSecretRef` holding the admin password and **`roles: [admin]`** — `spec.roles` is authoritative, so without it the operator revokes `admin` from the login it signs in with and every CR on the standalone goes `Forbidden`; such a user draws one `ValidationWarning` saying so (rule 211) — `Ready`, then deleted — Neo4j refuses to drop the user the operator is signed in as, so the user is `Failed` (reason `UserDeletionFailed`, message `deletion waits to remove user "neo4j" …`) with **one** Warning over the retries, keeps its finalizer, and about 5 minutes after the delete is gone with one `Released the finalizer without removing user "neo4j" …` Warning naming ``DROP USER `neo4j` ``, `neo4j` still in `SHOW USERS` (#549) |
| A standalone restart is not a transition of its databases (rule 183) | With a `Neo4jDatabase`, a `Neo4jCompositeDatabase` and a `Neo4jDatabaseAlias` on the standalone `Ready`, delete the standalone's pod three times, waiting for `Ready` each time: each stays phase `Ready` throughout, with `ClusterNotReady=True` while the pod is down (reason `ClusterNotReady`) and while the standalone reads `Ready` before Bolt accepts connections (reason `ClusterUnreachable`), then `ClusterNotReady=False` (`ClusterReady`); `kubectl get events --field-selector reason=DatabaseReady` (likewise `CompositeDatabaseReady`, `AliasReady`) still counts **one**, with **no** `ConnectionFailed` Warning and no ERROR line from their controllers. A database applied while the pod is down waits in `Pending` and announces `DatabaseReady` once when it is created. `kubectl get neo4jdatabase -o jsonpath='{..phase}'` never reads `Unknown` (rule 190) |
| The image's own JVM arguments (rule 212) | On the standalone: `kubectl exec <pod> -c neo4j -- grep -c '^server.jvm.additional=' /var/lib/neo4j/conf/neo4j.conf` counts the image's lines less `-XX:+AlwaysPreTouch` — 19 on 5.26, 23 on 2026.08+ — plus any of yours, the image's first; `grep -c AlwaysPreTouch` finds none unless you set it; under the phase's write load no server is OOMKilled (`grep -n` them: the `# operator:restart-neutral` block opens the file); `kubectl exec <pod> -c neo4j -- sh -c 'ps -eo args | grep -o -- "--add-[a-z]*=[^ ]*" | sort -u'` lists the four `--add-opens` (three on 5.26) and, on 2026.08+, `--add-modules=jdk.incubator.vector` (or `jcmd <pid> VM.command_line`). In the upgrade row, a standalone created by the previous release keeps its pod UID and `neo4j.com/config-hash` through the operator upgrade, its ConfigMap gains the block, and after `kubectl delete pod` the server runs the lines |
| Deleting during a restart leaves nothing behind (rule 178) | Create a throwaway `Neo4jUser`, `Neo4jRole`, `Neo4jDatabaseAlias` and `Neo4jDatabase`, and a `Neo4jRoleBinding` granting the role to a user created outside any `Neo4jUser` (`CREATE USER walkbound SET PASSWORD 'walkbound-pass' CHANGE NOT REQUIRED` in cypher-shell: a binding naming a user a `Neo4jUser` manages is refused, as it should be), all `Ready`. Delete the standalone's pod and, while it is down (`kubectl get neo4jenterprisestandalone` not `Ready`), delete the four CRs: each stays `Terminating` with phase `Failed` and `status.message` starting `deletion waits to remove`, **one** Warning each (`UserDeletionFailed`, `RoleDeletionFailed`, `BindingFailed`, `AliasFailed`; the database `DeletionFailed`, phase `Error`), and **no** ERROR line from their controllers. Once the standalone is back they are gone within about 30s, with no `NotFound` ERROR in the operator log as their finalizers are released (rule 189), and `SHOW USERS`, `SHOW ROLES`, `SHOW ALIASES FOR DATABASE`, `SHOW DATABASES` no longer list them (`walkbound` stays, without the role; drop it by hand afterwards). Repeat deleting them in the seconds the standalone reads `Ready` before Bolt accepts connections (delete the pod, then the CRs the moment it reads `Ready`): the same. The release after 5 minutes is the `neo4j` user's drop in the row above. Before, each was released at once (the alias waited for ever on a target that was not `Ready`) and stayed in Neo4j |
| A user with neither its cluster nor its Secret reports the cluster first (rule 182) | Apply a `Neo4jUser` naming a standalone and a password Secret that do not exist: phase `Pending`, reason `ClusterNotFound`, one `ClusterNotFound` Warning. Create the standalone: reason `SecretPending` once it exists. Create the Secret: `Ready` |
| A deleted target's volumes decide its dependents (rule 178) | On a throwaway standalone with `spec.storage.retentionPolicy: Delete` (the default) and a `Neo4jUser` `Ready` on it: delete the standalone, then the user — the user is gone within seconds, with **no** `UserDeletionFailed` Warning. Again with `retentionPolicy: Retain`: delete the standalone, wait until its CR is gone (its PVC stays), then delete the user — it stays `Terminating`, phase `Failed`, `status.message` naming `… was deleted and its volumes were kept`, one Warning. Create the standalone again with the same name (it mounts the kept volume): once it is `Ready`, the user is dropped and gone, and `SHOW USERS` on the new standalone no longer lists it. Delete the standalone and its PVC afterwards |
| **Upgrade from the previous release** (run FIRST, before building from `main`) | Install the previous release (`ghcr.io/priyolahiri/neo4j-kubernetes-operator:<previous tag>`), then create a standalone and a `Neo4jRole` with a few privileges under it. The first backup stays `Completed` after its Job's 30-minute TTL removes the Job — no second Job, no `Failed`. While a backup runs, `status.lastRunTime` does not move (`kubectl get neo4jbackup -w` shows no write every pass) |
| Sharded PVC backups are full | The scheduled sharded backup on a PVC with `backupType: AUTO` (or none): every run's `status.history[].shardArtifacts[].type` is `FULL` (the Job command carries `--type=FULL`), and a new `Neo4jShardedDatabase` with `seedBackupRef` to it seeds from the latest run (the seed proxy serves it, no `merge-chain` init container). A `Neo4jBackup` with `spec.shardedDatabase` and `backupType: DIFF` is refused by validation, naming `spec.options.backupType` (Neo4j does not back up property shards differentially). To reach the differential path, take an **all-databases** `AUTO` backup on a PVC twice: the second run raises a `BackupShardedDifferential` Warning naming the graph shard; a `seedBackupRef` to it → `Failed` within seconds, naming the differential shard, with **no** `backup-seed-proxy` Deployment; after a sharded backup's full run lands and `seedBackupRef` points at it, the database seeds on its own requeue |
| Sharded seed from MinIO | Back the sharded database up to MinIO. On a sharding cluster with **no** MinIO credentials or endpoint in its spec but `neo4j.com/auto-inherit-seed-creds: "true"`, a `seedBackupRef` to it: one `SeedCredsAutoInherited` event, the cluster gains the credentials in `extraEnvFrom` **and** `AWS_ENDPOINT_URL_S3` + `JAVA_TOOL_OPTIONS=-Daws.s3.forcePathStyle=true` in `spec.env` in **one** rolling restart, and the database seeds after it. | Shard language follows the parent | `SHOW DATABASES YIELD name, defaultLanguage WHERE name STARTS WITH '<logical>'` → the parent, `-g000` and every `-p00n` report the **same** language as the parent (measured 2026-09-29 on 2026.06.0: a parent created with `SET DEFAULT LANGUAGE CYPHER 5` on a `CYPHER_25` server gave a `CYPHER 5` family). | Sharded family language | The operator's `CREATE` (operator log, `Executing sharded database creation`) carries `SET DEFAULT LANGUAGE CYPHER 25` **exactly once**; the parent and every shard report `CYPHER 25` |
| Shard status (v1.18+) | `status.creationTime`, `graphShard`, `propertyShards` (one per shard, with its index) and `virtualDatabase` are populated, and agree with `SHOW DATABASES`: within ~15s of `Ready` every shard reads `state: online`, `ready: true`. On the v1.18.0 walk the graph shard read `starting` for minutes after the family was online, because the status was written once, right after `CREATE`, and not re-read before the five-minute periodic reconcile |
| **Upgrading a sharding cluster** from the previous release | Create the sharding cluster under the previous release, note the StatefulSet's `neo4j.com/cluster-template-hash` annotation (on the StatefulSet itself, not its pod template), its `metadata.generation`, and the pod UIDs, then upgrade to `main` (CRDs first). `status.effectiveCypherLanguage=CYPHER_25` (recorded from the ConfigMap the old operator wrote), the template hash and generation are **unchanged**, `neo4j.conf` differs only by settings `main` adds, each applied live with a `ConfigAppliedLive` event (from v1.20.x: the `dbms.cluster.network.connect_timeout` block), and **no pod restarted**. Then clear the stamp (`kubectl patch … --subresource=status --type=merge -p '{"status":{"effectiveCypherLanguage":null}}'`) and restart the operator — **scale it to 0 first**, or the running operator re-stamps the field before you can see it cleared: re-derived `CYPHER_25`, still no restart — the etcd-restore case |
| CLI: the sharded CR is legible | `status -n <ns>` lists the `Neo4jShardedDatabase` by its **CR `metadata.name`** — the same name vs. `spec.name` distinction the row above exists to catch — with its phase, alongside the cluster. `explain Neo4jShardedDatabase/<cr>` either decodes its conditions or says plainly that it carries none this CLI knows, which is the correct answer rather than a guess |

→ **Tear down**, then delete the Kind cluster.

### Phase 4 — Aura (no Kind deployment; needs Aura API credentials)

**BETA / best-effort surface.** The `Aura*` CRDs talk to the Aura cloud API, so

### Phase 5 — Cross-cluster replication (two deployments; sequential for backup mode, concurrent for network mode; needs `2026.08+`)

**Run this only when a `2026.08+` enterprise image is available.** Hosting a
replica requires it, and the check is enforced — on an older image the CR fails
with `ReplicaVersionTooOld` and nothing else in this phase can proceed. That is
itself scenario 1: confirm the gate fires rather than silently doing nothing.

Parts A/B below (backup mode, `source.mode: backup`) look like they break the
**one Enterprise deployment at a time** ground rule. They do not, and the
reason is the point of that mode: the two clusters are coupled **only through
the object store**, never over the network. So the upstream produces its
chain, gets torn down, and *then* the downstream comes up and pulls from the
bucket. Two deployments, never concurrent.

Network mode (`source.mode: network`, Parts C/D below) needs a live network
path, but "two clusters" doesn't mean leaving Kind or leaving this single
deployment session: Part C runs the real replication mechanism between two
`Neo4jEnterpriseCluster`s in different namespaces on **this same Kind
cluster**, reachable over ordinary in-cluster DNS — no proxy, no
`crossClusterReplication`, no LoadBalancer needed. Part D smoke-tests the
`crossClusterReplication` toggle on a single plain Kind cluster, where the
proxy's Service never gets an address. **Part E is the one that matters most**:
two Kind clusters, TLS on with mutual CA trust, the proxy holding a real
MetalLB address — the configuration CCDR is actually sold with, and the only
one that exercises the proxy, the certificate SANs, the advertised-address
override and cross-cluster trust together. See each part for what it does and
does not cover.

Stand up MinIO as the shared bucket (same pattern the backup specs use) for
Parts A/B.

**Part A — upstream (standalone is enough):**

| Scenario | Verify |
|---|---|
| Replication-source backup | `Neo4jBackup` `mode: replication-source` + `database` + `schedule` → `status.replicationPullURI` is populated and points at the chain directory. **Copy this value** |

| Replica seeds | `Neo4jReplicaDatabase` with `source.pullURI`/`seedURI` from Part A → phase `Replicating`; `SHOW DATABASES` shows `type=replica`, `access=read-only` on **every** copy including primaries. **Part E — the whole proxy path, two Kind clusters, TLS ON (two concurrent deployments):**

This is the configuration CCDR is actually sold with, and the only part that
exercises the proxy, the certificate SANs, the advertised-address override and
cross-cluster CA trust *together*. All of that was verified for the first time
on 2026-09-14, and three defects fell out of it that nothing else had reached
— run it before every release that touches CCDR or TLS.

```bash
make ccdr-e2e-up      # both Kind clusters, cert-manager + issuer, MetalLB on
                      # the upstream, the operator built from this tree on both
```

Then apply a `Neo4jEnterpriseCluster` to **each** — by hand, from the published
docs, because that is what is under test. Both get `spec.tls.mode:
cert-manager` with `strictPeerValidation: true` (the default) and 2 CI-sized
servers; the upstream also gets `spec.crossClusterReplication.enabled: true`.
Once both are `Ready`:

```bash
make ccdr-e2e-trust   # exchange the CAs, patch additionalClusterTrustCAs on both
make ccdr-e2e-status  # where everything is
make ccdr-e2e-down    # delete both clusters
```

The upstream defaults to the dev cluster (`neo4j-operator-dev`). To keep the dev
cluster beside the rig, set `CCDR_UPSTREAM_CLUSTER=<name>` on **every** target,
`down` included: without it they act on `neo4j-operator-dev`, and `down`
deletes it.

Put `--context` on every `kubectl` you run yourself. `kind create cluster`
switches the current context, and a batch of commands aimed at the wrong
cluster is the easiest mistake to make here — it produced a false blocker on
the first walk. The scripted steps already do.

| Scenario | Verify |
|---|---|
| CA exchange really crossed | copy each cluster's `ca.crt` out of its `<name>-tls-secret` into a Secret on the *other* cluster and reference it from `spec.tls.additionalClusterTrustCAs`. Then check it landed: `md5sum /ssl/trusted/*.crt` in each `server-0` — the upstream's `peer-ca-0.crt` must equal the downstream's own `ca.crt`, and vice versa. Both clusters must still reach `Ready`; a peer CA that stops a pod starting is a blocker, not a warning |

## Keeping this current

When you **add or change a capability**, update this page in the same PR:

1. Add a row to the **routing table** (which deployment, and *why* there).
2. Add the scenario + its in-DB check to the relevant **phase**.
3. Tick the **coverage** matrix.
4. If it changes the operator install or sizing, update the phase headers.
5. If it adds or changes a **CLI** command, put it in the phase whose
   deployment it reads — Phase 0 if it needs none, or a broken resource if what
   it reports is a failure. A command verified only against a healthy cluster
   is verified in the state nobody runs it in.

When a release fixes a specific bug, add a one-line scenario that would have
caught it (the v1.12.2 pass added the standalone-label, `system`-reject,
role-CR-name, and sharded-backup-by-CR-name checks). Record each run below.

The seed and pull are performed by the SERVER via the AWS SDK's default chain, which is why the credentials belong there — so this is a **documentation and failure-surface gap, not a missing feature**, and the earlier "cannot work against object storage" reading was too strong. `spec.source.credentialsSecretRef` is still consumed nowhere and is now documented as such on the field itself, in the guide, in the troubleshooting table and in the example. **Still worth fixing:** the CR stays `Seeding` with an optimistic message while the server refuses, and retries a permanent `ArgumentError` about once a second — the error never reaches `status.message`, which is what made this expensive to diagnose. |
